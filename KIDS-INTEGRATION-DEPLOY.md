# Ethan Kids: secure Ethan ID handoff (deployment required)

Hub now shows Ethan Kids as its 16th app entry **if the existing Hub catalogue has 15 other entries**. This build does not add or remove any other apps. Count is generated by Hub existing app catalogue.

1. Deploy ETHAN-HUB to hub.ethandigitalacademy.org and ETHAN-KIDS to kids.ethandigitalacademy.org. Keep both sites HTTPS.
2. In the EXISTING Ethan Hub Supabase project (configured in Hub and Kids config.js), run `supabase/KIDS-SECURE-SETUP.sql` in SQL Editor. Do not run in a new Supabase project.
3. In Supabase Edge Functions, deploy **ethan-sso-kids** from `supabase/functions/ethan-sso-kids/index.ts`. Set `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` as server-only secrets. Do not put service-role key in frontend, GitHub, or screenshots. Leave the existing `ethan-sso` function deployed for Ethan Cloud.
4. Configure ethan-sso-kids so the function can receive unauthenticated exchange requests (JWT verification disabled for this function only); the function itself validates the ticket and verifies the Ethan ID for create/verify. Set allowed origin to https://kids.ethandigitalacademy.org as in code. Configure Edge Function CORS separately if hosting policies require.
5. A trusted administrator must verify each adult outside the app, then approve their existing Ethan ID UUID in `ethan_kids_adults` using the example SQL comment. An Ethan ID account alone does NOT grant access. Do not automatically approve accounts based on self-declared account type.
6. Test with an approved account, an unapproved account, expired ticket, ticket replay, refresh/revisit, and sign out. Never put production tokens in chat or public logs.

**Limitations:** A client-side static website cannot protect public static HTML/assets from direct downloads. For strong child safety and private progress, migrate protected learning APIs and content to a server-side authorization layer. Handoff uses a short-lived single-use code; code redemption yields a Supabase session to the browser, so maintain strong HTTPS, CSP, and XSS protections. The legacy SSO function for other apps remains unchanged and should be audited separately.
